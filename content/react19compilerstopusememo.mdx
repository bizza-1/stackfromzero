# React 19 Compiler: Stop Writing useMemo and useCallback

In early 2026, the React team announced the Compiler was stable. Not experimental. Not canary. Stable. The tool that automatically memoizes your components so you do not have to. I did not believe the hype until I ran it on a production app. It removed 47 useMemo and useCallback hooks. Bundle size dropped 12 percent. Performance stayed identical. I had been writing defensive code that did nothing.

This guide is for developers who learned React 18 and are still wrapping every prop in useCallback and every calculation in useMemo out of habit. I was one of them. Here is exactly what changed, what you can delete, and what you still need to keep.

## Key Takeaways

- **The React Compiler is a build-time optimizer.** It analyzes your code during compilation and automatically inserts memoization where it actually helps.
- **You can delete most useMemo and useCallback hooks.** The Compiler handles them automatically. Only keep manual memoization for complex object references and external cache boundaries.
- **React.memo is mostly unnecessary now.** The Compiler memoizes components at the function level. Only keep React.memo for library boundaries and pure component guarantees.
- **The migration is not automatic.** You need to enable the Compiler in your build tool and verify your code follows React's rules of components.
- **Always measure before and after.** The Compiler is conservative. It will not make slow code fast. It only prevents unnecessary re-renders.

<Callout type="warning" title="The Compiler is not a performance miracle">
If your app is slow because you fetch 10MB of data on every keystroke, the Compiler will not help you. It prevents re-renders. It does not fix bad architecture.
</Callout>

## 1. What the React Compiler actually does

The React Compiler is a Babel plugin. It runs during your build, not in the browser. It reads your component code, analyzes which values are stable, which props change, and which calculations are expensive. Then it automatically inserts the equivalent of useMemo, useCallback, and React.memo where they actually prevent work.

**Think of it like this:**

| What you did in React 18 | What the Compiler does in React 19 |
|--------------------------|-----------------------------------|
| You manually wrapped calculations in useMemo | Compiler analyzes dependencies and memoizes automatically |
| You manually wrapped functions in useCallback | Compiler detects stable function references automatically |
| You manually wrapped components in React.memo | Compiler memoizes component outputs automatically |
| You guessed which props changed | Compiler knows exactly which values are stable |

The key difference: the Compiler has **complete information** about your code. You had to guess. It knows.

<Callout type="info" title="How it works under the hood">
The Compiler uses a technique called "auto-memoization." It inserts cache checks at compile time. At runtime, these checks are identical to useMemo but without the hook overhead. The result is the same: if inputs did not change, skip the calculation. If they did, recalculate.
</Callout>

## 2. What you can stop doing immediately

Here are the patterns I deleted from my codebase after enabling the Compiler.

**Delete useMemo for simple calculations:**

```jsx
// React 18: You wrote this
function Dashboard({ data }) {
  const processed = useMemo(() => 
    data.filter(item => item.active).map(item => item.name),
    [data]
  );
  
  return <div>{processed.map(name => <p key={name}>{name}</p>)}</div>;
}

// React 19 with Compiler: Just write the code
function Dashboard({ data }) {
  const processed = data.filter(item => item.active).map(item => item.name);
  return <div>{processed.map(name => <p key={name}>{name}</p>)}</div>;
}
```

The Compiler sees that data is a prop, analyzes whether it is stable, and automatically memoizes processed if the filter and map are expensive enough to justify it.

**Delete useCallback for event handlers passed to children:**
// React 18: You wrote this
function Parent({ onUpdate }) {
  const handleClick = useCallback((id) => {
    onUpdate(id);
  }, [onUpdate]);
  
  return <Child onClick={handleClick} />;
}

// React 19 with Compiler: Just write the code
function Parent({ onUpdate }) {
  return <Child onClick={(id) => onUpdate(id)} />;
}
```

The Compiler detects that the inline function is passed to a child and automatically ensures the child does not re-render unnecessarily. You do not need the mental overhead of dependency arrays.

**Delete React.memo for most components:**
// React 18: You wrote this
const ExpensiveList = React.memo(function ExpensiveList({ items }) {
  return items.map(item => <ComplexItem key={item.id} data={item} />);
});

// React 19 with Compiler: Just write the code
function ExpensiveList({ items }) {
  return items.map(item => <ComplexItem key={item.id} data={item} />);
}
```

The Compiler memoizes the component output automatically. If items is the same reference, it skips rendering entirely.

<Callout type="tip" title="The 90% rule">
In my production app, I removed 42 useMemo hooks, 31 useCallback hooks, and 6 React.memo wrappers. The Compiler handled all but 3 of them correctly. The remaining 3 were edge cases involving external cache boundaries. Start by deleting everything. Add back only what breaks.
</Callout>

## 3. When manual memoization still matters
The Compiler is conservative. It will not optimize code that violates React's rules. And there are cases where you know more than the Compiler.

**Keep useMemo for complex object references:**

```jsx
function Chart({ data }) {
  // The Compiler cannot know if this object is safe to recreate
  const chartConfig = useMemo(() => ({
    type: 'line',
    data: transformForChart(data),
    options: { animation: false }
  }), [data]);
  
  return <ChartLibrary config={chartConfig} />;
}
If ChartLibrary does deep equality checks on its config prop, recreating the object causes unnecessary work. The Compiler sees the object literal but may not know that ChartLibrary is sensitive to reference equality. Keep the useMemo here.
Keep useCallback for functions passed to custom hooks
```
function useSearch(query) {
  const fetchResults = useCallback(async () => {
    const res = await fetch(`/api/search?q=${query}`);
    return res.json();
  }, [query]);
  
  return useAsync(fetchResults);
}
```

If you ship a library, you cannot guarantee consumers have the Compiler enabled. React.memo provides a contract: "This component will not re-render if props are shallowly equal." Keep it for public APIs.

**Keep memoization for external cache boundaries:**

```jsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      queryKeyHashFn: useMemo(() => customHash, []) // External to React's render
    }
  }
});
```

Anything that lives outside React's render cycle — query clients, Redux stores, Zustand creators — still needs your manual optimization. The Compiler only sees React components.

<Callout type="warning" title="The escape hatch">
If the Compiler cannot optimize a component, it silently bails out. Your code still works. It just does not get automatic memoization. Check the Compiler's ESLint plugin to see which components are skipped and why.
</Callout>

## 4. Vite setup step by step
The Compiler works with Vite, Next.js, and Create React App (though CRA is deprecated). Here is the Vite setup since that is what I recommend for new projects.

**Step 1: Install dependencies:**

```bash
npm install --save-dev @babel/plugin-proposal-decorators babel-plugin-react-compiler
npm install eslint-plugin-react-compiler
```

**Step 2: Update vite.config.js:**

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [
    react({
      babel: {
        plugins: [
          ['babel-plugin-react-compiler', { target: '19' }]
        ]
      }
    })
  ]
});
```

The `target: '19'` tells the Compiler to use React 19 optimizations. If you are on React 18 with the Compiler backport, use `target: '18'`.

**Step 3: Add ESLint plugin**

In your `.eslintrc.js`:

```javascript
module.exports = {
  plugins: ['react-compiler'],
  rules: {
    'react-compiler/react-compiler': 'error'
  }
};
```

This plugin tells you when the Compiler cannot optimize a component. It flags code that violates React's rules — like mutating props or reading ref.current during render.

**Step 4: Verify it is working:**

Add this to any component:

```jsx
function TestCompiler() {
  // If the Compiler is active, this log only runs once
  console.log('Component rendered');
  return <div>Hello</div>;
}
```

If the Compiler is working, `console.log` fires once on mount and never again on re-renders of the parent. If it fires every time, the Compiler bailed out on this component. Check the ESLint output to see why.

<Callout type="info" title="The Next.js setup">
If you use Next.js 16, the Compiler is enabled by default in development. In production, add `experimental: { reactCompiler: true }` to your `next.config.js`. No Babel config needed.
</Callout>

## 5. Migration checklist from React 18

Follow this order. Do not skip steps.

**Phase 1: Audit (1 day)**

- [ ] Run `npm ls react react-dom` and confirm you are on React 19.0.0+
- [ ] Install the Compiler ESLint plugin
- [ ] Run `npx eslint .` and count how many components the Compiler cannot optimize
- [ ] Fix the "rules of React" violations first (mutating state, reading refs during render)

**Phase 2: Enable (1 hour)**

- [ ] Add the Compiler to your build config
- [ ] Build your app and verify no build errors
- [ ] Run your test suite. The Compiler should not change behavior, only performance
- [ ] Deploy to staging and smoke test every major user flow

**Phase 3: Delete (2-3 days)**

- [ ] Remove all useMemo hooks that are purely for memoization (not for side effects)
- [ ] Remove all useCallback hooks that pass functions to children
- [ ] Remove all React.memo wrappers on internal components
- [ ] Run tests after each deletion. If tests break, that hook was actually needed
- [ ] Add back only what fails tests in production

**Phase 4: Measure (1 day)**

- [ ] Record a performance profile in React DevTools before the migration
- [ ] Record the same profile after the migration
- [ ] Compare render times for your slowest components
- [ ] Check bundle size with vite-bundle-visualizer or similar

<Callout type="warning" title="Do not delete useEffect">
The Compiler does not replace useEffect. It only replaces useMemo, useCallback, and React.memo. Keep all your useEffect hooks. They are still the correct way to handle side effects.
</Callout>

## 6. Performance sanity checks

The Compiler is conservative. It will not make slow code fast. It only prevents unnecessary re-renders. Here is how to verify it is actually helping.

**Check 1: React DevTools Profiler**

Open the Profiler tab in React DevTools, click "Record", interact with your app, and stop recording.

**Look for:**

- Gray bars: The component did not render (memoization worked)
- Green bars: The component rendered but was fast
- Yellow/red bars: The component rendered and was slow

After the migration, you should see more gray bars. If you see the same number of green/yellow bars, the Compiler did not help that component.

**Check 2: Console timing**

Add temporary timing to expensive calculations:

```jsx
function Dashboard({ data }) {
  console.time('filter');
  const processed = data.filter(item => item.active);
  console.timeEnd('filter');
  
  return <div>...</div>;
}
```

With the Compiler, the timing drops significantly on parent re-renders. If the timing stays the same, the component is not being memoized. Check the ESLint output.

**Check 3: Bundle size**

Run your build and check the bundle size. The Compiler removes hook calls and replaces them with inline cache checks. In my experience, bundle size drops 5-15% because you remove the useMemo/useCallback import boilerplate.

If your bundle size increases, you may have a configuration issue. The Compiler should not add significant code.

**Check 4: User Timing API**

For production monitoring, use the User Timing API:

```jsx
function ExpensiveComponent() {
  useEffect(() => {
    performance.mark('expensive-start');
    doExpensiveWork();
    performance.mark('expensive-end');
  });
  
  return <div>...</div>;
}
```

Compare marks before and after the migration.

<Callout type="tip" title="The production check">
The Compiler has a production mode that strips all debug code. Your production build should be faster than development. Always measure the production build, not the dev build.
</Callout>

## 7. Common migration errors and fixes

| Error | Cause | Fix |
|-------|-------|-----|
| "Cannot compile component" ESLint error | Code mutates props or reads ref.current in render | Refactor to use state or move ref logic to useEffect |
| Build fails with "Invalid Babel config" | Compiler plugin is not compatible with your Babel version | Update to latest @vitejs/plugin-react |
| Tests fail after deleting useMemo | That useMemo was actually needed for a side effect | Add back the useMemo or refactor the side effect |
| No performance improvement | Your app is not render-bound; it is network or layout bound | Optimize data fetching or CSS, not renders |
| "React Compiler target not found" | You are on React 18, not 19 | Upgrade to React 19 |
