Building your first full-stack application is a rite of passage. You stop thinking about React and Spring Boot as separate subjects you study, and start thinking about them as two halves of one running system. In this tutorial we build that system together: a **Task Manager** app with a Spring Boot REST API on the back end and a React 18 single-page app on the front end.

By the end you will have written real Java and real JavaScript, wired them together over HTTP, handled loading and error states like a professional, and understood exactly what happens on every request. No magic, no skipped steps.

<Callout type="tip" title="What you'll build">
A Task Manager where users can create tasks, mark them complete, and delete them. The React front end talks to a Spring Boot API, which persists data with Spring Data JPA and an in-memory H2 database. Everything runs locally and is ready to deploy.
</Callout>

## What you'll need

Before we start writing code, make sure your machine is ready. You need surprisingly little.

- **Java 17 or newer.** Spring Boot 3 requires Java 17 as a baseline. Run `java -version` to check.
- **Node.js 18 or newer.** React 18 and modern build tools assume a recent Node. Run `node -v` to check.
- **A code editor.** IntelliJ IDEA (Community Edition is free) is fantastic for Java. VS Code is great for React. Many people run both side by side, and that's exactly what we'll do.
- **Basic JavaScript and a little Java.** You don't need to be an expert. If you can write a function and a loop, you're ready.

That's it. We use free, open-source tools throughout. You will not spend a single naira to follow along.

## Understanding the architecture

It helps to picture the whole system before we build any part of it. A full-stack app is really two programs having a conversation.

The **back end** (Spring Boot) owns the data. It exposes a set of URLs — the API — that the outside world can call. When a request comes in, it does some work (reads or writes the database) and sends back JSON.

The **front end** (React) owns what the user sees. It runs in the browser, renders the interface, and calls the back-end API whenever it needs data. The user never talks to the database directly; they talk to React, which talks to Spring Boot, which talks to the database.

The contract between them is HTTP and JSON. As long as both sides agree on the shape of that JSON, they can be developed independently. This separation is the single most important idea in full-stack development.

## Modeling the data with JPA

Every task has an id, a title, and a boolean telling us whether it's done. In Spring Data JPA we express that as an `@Entity` class. Create a new file `Task.java`:

```java
package com.stackfromzero.taskmanager;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private boolean completed;

    // JPA requires a no-args constructor
    public Task() {
    }

    public Task(String title, boolean completed) {
        this.title = title;
        this.completed = completed;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public boolean isCompleted() {
        return completed;
    }

    public void setCompleted(boolean completed) {
        this.completed = completed;
    }
}
```

The `@Entity` annotation tells Hibernate this class maps to a database table. The `@Id` and `@GeneratedValue` annotations mark `id` as the primary key, auto-generated by the database. The getters and setters let Jackson (Spring's JSON library) serialize the object to and from JSON.

## Creating the repository

Here is where Spring Boot feels like magic — but it isn't, it's just a well-designed abstraction. To get full CRUD database access, you write an *interface* and Spring generates the implementation at runtime.

```java
package com.stackfromzero.taskmanager;

import org.springframework.data.jpa.repository.JpaRepository;

public interface TaskRepository extends JpaRepository<Task, Long> {
    // findAll(), findById(), save(), deleteById() are all provided for free
}
```

By extending `JpaRepository<Task, Long>` — where `Task` is the entity and `Long` is the type of its id — you inherit `findAll()`, `save()`, `deleteById()`, and more. You never write a line of SQL for basic operations.

## Building the REST controller

The controller is the front door of your API. It maps HTTP requests to Java methods. Create `TaskController.java`:

```java
package com.stackfromzero.taskmanager;

import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api/tasks")
@CrossOrigin(origins = "http://localhost:5173")
public class TaskController {

    private final TaskRepository repository;

    public TaskController(TaskRepository repository) {
        this.repository = repository;
    }

    @GetMapping
    public List<Task> getAllTasks() {
        return repository.findAll();
    }

    @PostMapping
    public Task createTask(@RequestBody Task task) {
        return repository.save(task);
    }

    @PutMapping("/{id}")
    public Task updateTask(@PathVariable Long id, @RequestBody Task updated) {
        Task task = repository.findById(id)
                .orElseThrow(() -> new RuntimeException("Task not found"));
        task.setTitle(updated.getTitle());
        task.setCompleted(updated.isCompleted());
        return repository.save(task);
    }

    @DeleteMapping("/{id}")
    public void deleteTask(@PathVariable Long id) {
        repository.deleteById(id);
    }
}
```

A few things to notice here. `@RestController` combines `@Controller` and `@ResponseBody`, meaning every return value is automatically serialized to JSON. `@RequestMapping("/api/tasks")` sets the base path for every method. The `@CrossOrigin` annotation is critical: it tells the browser that our React app, running on port 5173, is allowed to call this API. Without it, the browser blocks the request with a CORS error.

<Callout type="warning" title="CORS in production">
The hard-coded `http://localhost:5173` origin is fine for local development, but never ship it to production. In a real deployment you'd read allowed origins from configuration and set them per environment. We'll cover that in a later guide.
</Callout>

Constructor injection — passing `TaskRepository` into the constructor — is the recommended way to get dependencies in Spring. It makes the class easy to test and its dependencies explicit.

Now run the app. In IntelliJ, click the green run arrow next to `TaskmanagerApplication`, or from the terminal:


Your API is now live at `http://localhost:8080/api/tasks`. Test it with curl:

## Scaffolding the React front end

Open a second terminal — leave Spring Boot running in the first — and create the React app with Vite, the fast modern build tool:

```bash
npm create vite@latest task-frontend -- --template react
cd task-frontend
npm install
npm run dev
```

Vite starts a dev server on `http://localhost:5173` with instant hot-module reloading. Every time you save a file, the browser updates without a full refresh, which keeps you in flow. The generated project is intentionally minimal: an `index.html`, a `src/main.jsx` entry point, and a `src/App.jsx` component. We'll do most of our work in `App.jsx`.

Before writing components, it helps to agree on how we structure them. We'll keep one top-level `App` component that owns all the state and data-fetching, and pass data down to small presentational components through props. This "smart parent, dumb children" pattern is the simplest architecture that scales, and it keeps your data flow easy to follow: state lives in one place and flows downward, while events flow upward through callback props.

```jsx
// A small presentational component — it renders, it doesn't fetch
function TaskItem({ task, onToggle, onDelete }) {
  return (
    <li className="d-flex align-items-center gap-2">
      <input
        type="checkbox"
        checked={task.completed}
        onChange={() => onToggle(task)}
      />
      <span style={{ textDecoration: task.completed ? "line-through" : "none" }}>
        {task.title}
      </span>
      <button onClick={() => onDelete(task.id)}>Delete</button>
    </li>
  );
}
```

`TaskItem` knows nothing about the API or `fetch`. It receives a task and two callbacks, renders a checkbox and a delete button, and calls those callbacks when the user interacts. This is what makes it reusable and trivial to test — it's a pure function of its props.

## Fetching data from the API

Let's replace the starter content. The core of a React data-fetching component is the `useEffect` and `useState` hooks working together. Open `src/App.jsx`:

```jsx
import { useState, useEffect } from "react";

const API_URL = "http://localhost:8080/api/tasks";

function App() {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch(API_URL)
      .then((res) => {
        if (!res.ok) throw new Error("Failed to load tasks");
        return res.json();
      })
      .then((data) => setTasks(data))
      .catch((err) => setError(err.message))
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <p>Loading tasks...</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <div>
      <h1>My Tasks</h1>
      <ul>
        {tasks.map((task) => (
          <li key={task.id}>{task.title}</li>
        ))}
      </ul>
    </div>
  );
}

export default App;
```

The empty dependency array `[]` in `useEffect` means "run this once, after the first render." We track three pieces of state — the tasks, whether we're still loading, and any error — because a real UI has to handle all three cases. Beginners often forget the loading and error states, then wonder why their app flickers or shows a blank screen. Don't be that developer.

## Adding and completing tasks

Reading data is only half the story. Let's add functions to create and toggle tasks. Add these inside the `App` component:

```jsx
async function addTask(title) {
  const res = await fetch(API_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title, completed: false }),
  });
  const newTask = await res.json();
  setTasks((prev) => [...prev, newTask]);
}

async function toggleTask(task) {
  const res = await fetch(`${API_URL}/${task.id}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ ...task, completed: !task.completed }),
  });
  const updated = await res.json();
  setTasks((prev) => prev.map((t) => (t.id === updated.id ? updated : t)));
}

async function deleteTask(id) {
  await fetch(`${API_URL}/${id}`, { method: "DELETE" });
  setTasks((prev) => prev.filter((t) => t.id !== id));
}
```

Notice the pattern: we call the API, wait for the response, and *then* update local state to match. This keeps the UI in sync with the database. When we update state we always use the functional form — `setTasks((prev) => ...)` — because it guarantees we're working with the latest state, not a stale snapshot.

## Wiring up the form

A small form component ties it together. Here's a complete, interactive `App.jsx` body you can drop in:

```jsx
import { useState } from "react";

function TaskForm({ onAdd }) {
  const [title, setTitle] = useState("");

  function handleSubmit(e) {
    e.preventDefault();
    if (!title.trim()) return;
    onAdd(title.trim());
    setTitle("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="What needs doing?"
      />
      <button type="submit">Add</button>
    </form>
  );
}
```

Calling `e.preventDefault()` stops the browser from reloading the page on submit — a classic gotcha. We guard against empty titles with `title.trim()`, then lift the value up to the parent through the `onAdd` callback. This is the standard React pattern: child components report events upward, parents own the state.

## Handling errors gracefully

Networks fail. Servers restart. A production app must survive both. Wrap your fetch calls in `try/catch` and surface a friendly message rather than letting the app crash:

```jsx
async function addTask(title) {
  try {
    const res = await fetch(API_URL, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ title, completed: false }),
    });
    if (!res.ok) throw new Error("Could not save the task");
    const newTask = await res.json();
    setTasks((prev) => [...prev, newTask]);
  } catch (err) {
    setError(err.message);
  }
}
```

<Callout type="info" title="Optimistic updates">
For an even snappier feel, you can update the UI immediately and roll back only if the request fails. That's called an optimistic update. It's a great next step once you're comfortable with the basic flow shown here.
</Callout>

## Understanding the request lifecycle

It's worth slowing down to trace a single click through the entire stack, because this is the mental model that makes everything else make sense. Imagine the user types "Buy groceries" and clicks *Add*.

First, the React form's submit handler fires. It calls `addTask("Buy groceries")`, which builds a `fetch` request with the JSON body `{"title":"Buy groceries","completed":false}` and sends it to `http://localhost:8080/api/tasks`. The browser opens an HTTP connection, but before the real request it may send a CORS preflight `OPTIONS` request to ask the server whether this origin is allowed. Because we added `@CrossOrigin`, Spring answers yes.

The `POST` then arrives at Spring Boot. The dispatcher servlet matches the URL and HTTP method to our `createTask` method. Jackson deserializes the JSON body into a `Task` object. Spring passes it to `repository.save(task)`, which Hibernate translates into an SQL `INSERT`. The database assigns an auto-generated id and returns it. The saved `Task` — now with an id — bubbles back up, Jackson serializes it to JSON, and Spring sends a `200 OK` response.

Back in the browser, our `await res.json()` resolves with the new task, and `setTasks` adds it to state. React re-renders, and the new task appears on screen. That entire round trip usually takes a few milliseconds locally. Every feature you ever build is a variation on this one loop: event, request, work, response, re-render.

## Handling loading and error states

A demo that only works when everything goes right is not production-ready. Real networks are slow and sometimes fail, so we track three pieces of UI state: the data, whether we're loading, and any error. Here's the pattern inside the React component:

```jsx
import { useEffect, useState } from "react";

const API_URL = "http://localhost:8080/api/tasks";

function App() {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    async function loadTasks() {
      try {
        const res = await fetch(API_URL);
        if (!res.ok) throw new Error("Failed to load tasks");
        setTasks(await res.json());
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }
    loadTasks();
  }, []);

  if (loading) return <p>Loading your tasks...</p>;
  if (error) return <p className="text-danger">{error}</p>;

  return <TaskList tasks={tasks} />;
}
```

The `useEffect` with an empty dependency array runs exactly once, after the first render — the perfect place to fetch initial data. The `finally` block guarantees we stop showing the loading spinner whether the request succeeds or fails. Users always know what state the app is in, which is the difference between an app that feels broken and one that feels solid.

## Deleting and toggling tasks

The remaining two operations follow the same shape as creating. To delete, we call the API and then remove the task from state:

```jsx
async function deleteTask(id) {
  try {
    const res = await fetch(`${API_URL}/${id}`, { method: "DELETE" });
    if (!res.ok) throw new Error("Could not delete the task");
    setTasks((prev) => prev.filter((task) => task.id !== id));
  } catch (err) {
    setError(err.message);
  }
}

async function toggleTask(task) {
  try {
    const res = await fetch(`${API_URL}/${task.id}`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ ...task, completed: !task.completed }),
    });
    if (!res.ok) throw new Error("Could not update the task");
    const updated = await res.json();
    setTasks((prev) => prev.map((t) => (t.id === updated.id ? updated : t)));
  } catch (err) {
    setError(err.message);
  }
}
```

Notice how we never mutate state directly. `filter` and `map` return brand-new arrays, and the spread operator `{ ...task, completed: !task.completed }` builds a new object. React relies on these new references to know when to re-render. Mutating the existing array in place is one of the most common beginner bugs, and it produces the maddening symptom of "my data changed but the screen didn't." Treat state as read-only and always replace it.

## Common problems and fixes

**CORS error in the console.** The browser is blocking the request. Double-check the `@CrossOrigin` origin matches your React dev server's exact URL and port.

**Connection refused.** Your Spring Boot server isn't running, or it's on a different port. Confirm it started cleanly and check the port in the startup logs.

**Tasks disappear on restart.** That's expected with an in-memory H2 database — it resets every time the server restarts. Switch to PostgreSQL when you're ready for persistent storage.
