Your first full-stack build changes how you think about the pieces. React and Spring Boot stop being two separate things you studied in isolation. They become one system you understand end to end. In this tutorial, you'll build that system: a **Task Manager** app with a Spring Boot REST API on the back end and a React 18 single-page app on the front end.

By the end, you'll have written real Java and real JavaScript. You'll have wired them together over HTTP, handled loading and error states the way a professional does, and traced exactly what happens on every request. No skipped steps.

<Callout type="tip" title="What you'll build">
You'll build a Task Manager where users can create tasks, check them off, and delete them. The React front end talks to a Spring Boot API, and that API stores data with Spring Data JPA in an in-memory H2 database. Everything runs on your machine, and it's ready to deploy when you are.
</Callout>

## What you'll need

Before you write any code, check that your machine has what it needs. The list is short.

- **Java 17 or newer.** Spring Boot 3 needs Java 17 as a minimum. Run `java -version` to check yours.
- **Node.js 18 or newer.** React 18 and current build tools expect a recent Node version. Run `node -v` to check.
- **A code editor.** IntelliJ IDEA (the free Community Edition works fine) handles Java well. VS Code handles React well. Plenty of developers run both at once, and that's what we'll do here.
- **Basic JavaScript and a little Java.** You don't need deep expertise. If you can write a function and a loop, you have enough to start.

That covers it. Every tool here is free and open source, so this won't cost you a single naira to follow along.

## Understanding the architecture

Picture the whole system before you build any part of it. A full-stack app is really two programs that exchange data with each other.

The back end (Spring Boot) owns the data. It exposes a set of URLs, the API, that the outside world can call. When a request comes in, it does some work (reads or writes the database) and sends back JSON.

The front end (React) owns what the user sees. It runs in the browser, renders the interface, and calls the back-end API whenever it needs data. The user never talks to the database directly. They talk to React, and React talks to Spring Boot, and Spring Boot talks to the database.

The contract between the two sides is HTTP and JSON. As long as both agree on the shape of that JSON, you can build them independently. This separation is the single most important idea in full-stack development.

## Modeling the data with JPA

Every task needs an id, a title, and a boolean that tracks whether it's done. In Spring Data JPA, you express that as an `@Entity` class. Create a new file called `Task.java`:

```java
package com.stackfromzero.taskmanager;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private boolean completed;

    // JPA requires a no-args constructor
    public Task() {
    }

    public Task(String title, boolean completed) {
        this.title = title;
        this.completed = completed;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public boolean isCompleted() {
        return completed;
    }

    public void setCompleted(boolean completed) {
        this.completed = completed;
    }
}
```

The `@Entity` annotation tells Hibernate that this class maps to a database table. `@Id` and `@GeneratedValue` mark `id` as the primary key, auto-generated by the database. The getters and setters let Jackson, Spring's JSON library, serialize the object to and from JSON.

## Creating the repository

This next part looks surprising the first time you see it, though it's really just a well-designed abstraction. To get full CRUD access to the database, you write an *interface*, and Spring generates the implementation for you at runtime.

```java
package com.stackfromzero.taskmanager;

import org.springframework.data.jpa.repository.JpaRepository;

public interface TaskRepository extends JpaRepository<Task, Long> {
    // findAll(), findById(), save(), deleteById() are all provided for free
}
```

Here, `Task` is the entity and `Long` is the type of its id. Extend `JpaRepository<Task, Long>` and you inherit `findAll()`, `save()`, `deleteById()`, and more, all without writing a line of SQL for basic operations.

## Building the REST controller

The controller handles every HTTP request that reaches your API and routes it to the right Java method. Create `TaskController.java`:

```java
package com.stackfromzero.taskmanager;

import org.springframework.web.bind.annotation.*;
import java.util.List;

@RestController
@RequestMapping("/api/tasks")
@CrossOrigin(origins = "http://localhost:5173")
public class TaskController {

    private final TaskRepository repository;

    public TaskController(TaskRepository repository) {
        this.repository = repository;
    }

    @GetMapping
    public List<Task> getAllTasks() {
        return repository.findAll();
    }

    @PostMapping
    public Task createTask(@RequestBody Task task) {
        return repository.save(task);
    }

    @PutMapping("/{id}")
    public Task updateTask(@PathVariable Long id, @RequestBody Task updated) {
        Task task = repository.findById(id)
                .orElseThrow(() -> new RuntimeException("Task not found"));
        task.setTitle(updated.getTitle());
        task.setCompleted(updated.isCompleted());
        return repository.save(task);
    }

    @DeleteMapping("/{id}")
    public void deleteTask(@PathVariable Long id) {
        repository.deleteById(id);
    }
}
```

A few details matter here. `@RestController` combines `@Controller` and `@ResponseBody`, so every return value gets serialized to JSON automatically. `@RequestMapping("/api/tasks")` sets the base path for every method in the class. The `@CrossOrigin` annotation matters most: it tells the browser that your React app, running on port 5173, has permission to call this API. Skip it, and the browser blocks the request with a CORS error.

<Callout type="warning" title="CORS in production">
The hard-coded `http://localhost:5173` origin works fine for local development, but don't ship it to production. In a real deployment, you'd read allowed origins from configuration and set them per environment. A later guide covers that.
</Callout>

Constructor injection, passing `TaskRepository` into the constructor, is the recommended way to get dependencies in Spring. It keeps the class easy to test and makes its dependencies explicit.

Now run the app. In IntelliJ, click the green run arrow next to `TaskmanagerApplication`, or from the terminal:

```bash

```

Your API is now live at `http://localhost:8080/api/tasks`. Test it with curl:

## Scaffolding the React front end

Open a second terminal (leave Spring Boot running in the first) and create the React app with Vite, the fast modern build tool:

```bash
npm create vite@latest task-frontend -- --template react
cd task-frontend
npm install
npm run dev
```

Vite starts a dev server on `http://localhost:5173` with instant hot-module reloading. Every time you save a file, the browser updates without a full refresh, so you don't lose time waiting on rebuilds. The generated project stays intentionally minimal: an `index.html` file, a `src/main.jsx` entry point, and a `src/App.jsx` component. Most of the work happens in `App.jsx`.

Before writing components, decide how to structure them. Keep one top-level `App` component that owns all the state and data-fetching, then pass data down to small presentational components through props. This "smart parent, dumb children" pattern is simple, and it scales well. State lives in one place and flows downward. Events flow upward through callback props.

```jsx
// A small presentational component: it renders, it doesn't fetch
function TaskItem({ task, onToggle, onDelete }) {
  return (
    <li className="d-flex align-items-center gap-2">
      <input
        type="checkbox"
        checked={task.completed}
        onChange={() => onToggle(task)}
      />
      <span style={{ textDecoration: task.completed ? "line-through" : "none" }}>
        {task.title}
      </span>
      <button onClick={() => onDelete(task.id)}>Delete</button>
    </li>
  );
}
```

`TaskItem` knows nothing about the API or `fetch`. It receives a task and two callbacks, renders a checkbox and a delete button, and calls those callbacks when the user interacts with it. That's what makes it reusable and easy to test: it's a pure function of its props.

## Fetching data from the API

Time to replace the starter content. The core of a React data-fetching component is the `useEffect` and `useState` hooks working together. Open `src/App.jsx`:

```jsx
import { useState, useEffect } from "react";

const API_URL = "http://localhost:8080/api/tasks";

function App() {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch(API_URL)
      .then((res) => {
        if (!res.ok) throw new Error("Failed to load tasks");
        return res.json();
      })
      .then((data) => setTasks(data))
      .catch((err) => setError(err.message))
      .finally(() => setLoading(false));
  }, []);

  if (loading) return <p>Loading tasks...</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <div>
      <h1>My Tasks</h1>
      <ul>
        {tasks.map((task) => (
          <li key={task.id}>{task.title}</li>
        ))}
      </ul>
    </div>
  );
}

export default App;
```

The empty dependency array `[]` in `useEffect` means run this once, after the first render. You're tracking three pieces of state: the tasks, whether you're still loading, and any error, because a real UI has to handle all three cases. Beginners often skip the loading and error states, then wonder why their app flickers or shows a blank screen. Handle both from the start and save yourself the confusion.

## Adding and completing tasks

Reading data only covers half the job. Now add functions to create and toggle tasks, inside the `App` component:

```jsx
async function addTask(title) {
  const res = await fetch(API_URL, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title, completed: false }),
  });
  const newTask = await res.json();
  setTasks((prev) => [...prev, newTask]);
}

async function toggleTask(task) {
  const res = await fetch(`${API_URL}/${task.id}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ ...task, completed: !task.completed }),
  });
  const updated = await res.json();
  setTasks((prev) => prev.map((t) => (t.id === updated.id ? updated : t)));
}

async function deleteTask(id) {
  await fetch(`${API_URL}/${id}`, { method: "DELETE" });
  setTasks((prev) => prev.filter((t) => t.id !== id));
}
```

The pattern stays consistent: call the API, wait for the response, then update local state to match it. This keeps the UI in sync with the database. When you update state, always use the functional form, `setTasks((prev) => ...)`, because it guarantees you're working with the latest state instead of a stale snapshot.

## Wiring up the form

A small form component ties it together. Here's the `TaskForm` component you can drop in:

```jsx
import { useState } from "react";

function TaskForm({ onAdd }) {
  const [title, setTitle] = useState("");

  function handleSubmit(e) {
    e.preventDefault();
    if (!title.trim()) return;
    onAdd(title.trim());
    setTitle("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="What needs doing?"
      />
      <button type="submit">Add</button>
    </form>
  );
}
```

Calling `e.preventDefault()` stops the browser from reloading the page on submit. Skip it, and every form submission refreshes the whole app. The `title.trim()` check guards against empty titles, and the value then moves up to the parent through the `onAdd` callback. That's the standard React pattern: child components report events upward, and parents own the state.

## Handling errors gracefully

Networks fail sometimes. Servers restart sometimes. A production app needs to survive both. Wrap your fetch calls in `try/catch` and show a clear message instead of letting the app crash:

```jsx
async function addTask(title) {
  try {
    const res = await fetch(API_URL, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ title, completed: false }),
    });
    if (!res.ok) throw new Error("Could not save the task");
    const newTask = await res.json();
    setTasks((prev) => [...prev, newTask]);
  } catch (err) {
    setError(err.message);
  }
}
```

<Callout type="info" title="Optimistic updates">
For a faster feel, you can update the UI right away and roll back only if the request fails. This is called an optimistic update, and it's a solid next step once you're comfortable with the basic flow shown here.
</Callout>

## Understanding the request lifecycle

It's worth slowing down to trace a single click through the whole stack, because this is the mental model that makes everything else make sense. Say the user types "Buy groceries" and hits *Add*.

First, the React form's submit handler fires. It calls `addTask("Buy groceries")`, which builds a `fetch` request with the JSON body `{"title":"Buy groceries","completed":false}` and sends it to `http://localhost:8080/api/tasks`. The browser opens an HTTP connection, but before the real request, it may send a CORS preflight `OPTIONS` request asking the server whether this origin is allowed. Because you added `@CrossOrigin`, Spring answers yes.

The `POST` request then arrives at Spring Boot. The dispatcher servlet matches the URL and HTTP method to your `createTask` method. Jackson deserializes the JSON body into a `Task` object. Spring passes it to `repository.save(task)`, and Hibernate translates that into an SQL `INSERT`. The database assigns an auto-generated id and returns it. The saved `Task`, now with an id attached, travels back up. Jackson serializes it to JSON, and Spring sends a `200 OK` response.

Back in the browser, `await res.json()` resolves with the new task, and `setTasks` adds it to state. React re-renders, and the new task shows up on screen. The whole round trip usually takes a few milliseconds locally. Every feature you build after this is a variation on the same loop: event, request, work, response, re-render.

## Handling loading and error states

A demo that only works when everything goes right isn't production-ready. Real networks are slow, and they fail sometimes, so track three pieces of UI state: the data, whether you're loading, and any error. Here's that pattern inside the React component:

```jsx
import { useEffect, useState } from "react";

const API_URL = "http://localhost:8080/api/tasks";

function App() {
  const [tasks, setTasks] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    async function loadTasks() {
      try {
        const res = await fetch(API_URL);
        if (!res.ok) throw new Error("Failed to load tasks");
        setTasks(await res.json());
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }
    loadTasks();
  }, []);

  if (loading) return <p>Loading your tasks...</p>;
  if (error) return <p className="text-danger">{error}</p>;

  return <TaskList tasks={tasks} />;
}
```

The `useEffect` with an empty dependency array runs exactly once, after the first render. That makes it the right place to fetch initial data. The `finally` block guarantees the loading spinner disappears whether the request succeeds or fails. Users always know what state the app is in, and that's the difference between an app that feels broken and one that feels solid.

## Deleting and toggling tasks

The remaining two operations follow the same shape as creating a task. To delete one, call the API and then remove it from state:

```jsx
async function deleteTask(id) {
  try {
    const res = await fetch(`${API_URL}/${id}`, { method: "DELETE" });
    if (!res.ok) throw new Error("Could not delete the task");
    setTasks((prev) => prev.filter((task) => task.id !== id));
  } catch (err) {
    setError(err.message);
  }
}

async function toggleTask(task) {
  try {
    const res = await fetch(`${API_URL}/${task.id}`, {
      method: "PUT",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ ...task, completed: !task.completed }),
    });
    if (!res.ok) throw new Error("Could not update the task");
    const updated = await res.json();
    setTasks((prev) => prev.map((t) => (t.id === updated.id ? updated : t)));
  } catch (err) {
    setError(err.message);
  }
}
```

Notice that state never gets mutated directly here. `filter` and `map` return brand-new arrays, and the spread operator `{ ...task, completed: !task.completed }` builds a new object. React relies on these new references to know when to re-render. Mutating the existing array in place is one of the most common beginner bugs, and it causes that frustrating symptom where your data changed but the screen didn't. Treat state as read-only, and always replace it instead of editing it.

With Spring Boot running on 8080 and React on 5173, open the app in your browser. Add a task and watch it appear. This is the moment full-stack development clicks: the task you typed into a React input is now a row in a database that Java manages.

## Common problems and fixes

**CORS error in the console.** The browser is blocking the request. Check that the `@CrossOrigin` origin matches your React dev server's exact URL and port.

**Connection refused.** Your Spring Boot server isn't running, or it's running on a different port. Confirm it started cleanly, and check the port in the startup logs.

**Tasks disappear on restart.** That's expected with an in-memory H2 database. It resets every time the server restarts. Switch to PostgreSQL once you need data to persist.
